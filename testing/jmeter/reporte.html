¿Qué es esto y cómo se hizo?

Este proyecto (Invernadero Monitor) es un sistema de monitoreo con Arduino, una app Android y Firebase. Para el curso de Validación y Pruebas de Software, además de las pruebas normales de la app, se armó un plan de pruebas automatizado con Apache JMeter que ataca directamente la base de datos en la nube (Firebase Realtime Database), sin necesidad de tener el celular ni el Arduino encendidos.

1
Configuración compartidaSe define una sola vez el dominio de Firebase y el header Content-Type: application/json, para que todas las peticiones de abajo lo reutilicen.
2
Grupo 1 — Seguridad4 peticiones puntuales sin credenciales (leer, escribir, escribir un dato inválido, y pedir un nodo que no existe en las reglas). Cada una debe recibir 401 Permission denied.
3
Grupo 2 — RendimientoLa misma lectura, repetida muchas veces en paralelo (usuarios simulados concurrentes) para medir cuánto tarda Firebase en responder bajo carga.
4
Recolección de resultadosJMeter guarda cada petición (código de respuesta, tiempo, si pasó la validación) en un archivo, con el que se arma este reporte.
Grupo 1

Seguridad sin autenticar

  • 1 usuario, corre una sola vez
  • Verifica que las reglas de Firebase bloqueen todo acceso sin sesión
  • Cada petición valida el código de respuesta, y una de ellas también el texto exacto del error
Grupo 2

Rendimiento bajo carga

  • Usuarios, repeticiones y rampa de arranque son parámetros, no están fijos en el archivo
  • Ejemplo real usado: -Jusers=20 -Jloops=15 -Jrampup=5 → 300 peticiones
  • Mide la latencia de Firebase, no la app: mismo endpoint, sin token

Ser parametrizable significa que el mismo archivo sirve para correr una prueba rápida con 1 usuario o una carga real con 50, sin editar nada — solo cambia el comando con el que se ejecuta. El archivo se llama firebase_security_performance.jmx y queda versionado en el repositorio del proyecto, así cualquiera puede volver a correrlo para confirmar que las reglas de seguridad siguen funcionando.

Glosario rápido (si es tu primera vez con JMeter o pruebas de carga):

401
Código HTTP que significa "no autorizado". Es la respuesta que Firebase manda cuando falta iniciar sesión.
Permission denied
El mensaje exacto que Firebase pone dentro de la respuesta 401, confirmando que el rechazo fue por permisos y no por otro error.
Usuario concurrente (en JMeter)
Un "hilo" que manda peticiones de forma independiente y al mismo tiempo que los demás, simulando a una persona real usando la app.
Rampa de arranque
Cuántos segundos tarda JMeter en arrancar a todos los usuarios. Con rampa de 5 s y 20 usuarios, arranca uno cada 0.25 s en vez de los 20 de golpe.
Percentil (p50, p90, p99)
p50 = la mitad de las peticiones respondió en ese tiempo o menos. p90 = el 90% lo hizo en ese tiempo o menos. p99 mide casi el peor caso (el 1% más lento).
req/s
Peticiones por segundo: cuántas peticiones completas maneja el sistema en promedio durante la prueba.

1. Seguridad — acceso sin autenticar

Cuatro casos puntuales contra las reglas publicadas en database.rules.json. En los cuatro se espera 401 Permission denied, sin excepción.

Lectura de temperatura sin token Por qué: si esto no estuviera bloqueado, cualquiera con la URL podría ver los datos del invernadero sin permiso. GET /temperature/current.json 401 ✓ 401

Nota de interpretación. El dashboard propio de JMeter marca estas 304 muestras como 100% Error. Eso es solo porque JMeter cuenta cualquier HTTP 4xx como fallo por convención — no significa que la prueba haya fallado. Aquí, provocar el 401 en el 100% de los casos es el resultado correcto: confirma que las reglas de Firebase rechazan todo acceso sin autenticar, incluso bajo carga concurrente.
